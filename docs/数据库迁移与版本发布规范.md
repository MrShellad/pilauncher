# PiLauncher 数据库迁移与版本发布规范

## 1. 目的与适用范围

本规范用于防止 PiLauncher 在版本升级后因数据库迁移不兼容、同版本产物不一致或发布流程失控而出现启动闪退、白框退出及用户数据不可用。

适用范围：

- `src-tauri/migrations/` 下的所有 SQLx 迁移。
- `src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 和 `src-tauri/tauri.conf.json` 中的版本信息。
- Windows、Linux、macOS 及移动端的正式构建与发布流程。
- 自动更新服务、安装包、签名文件和回滚版本。
- 涉及 SQLite 表、索引、触发器、迁移元数据和种子数据的改动。

本文中的规则等级：

- **必须/禁止**：发布阻断项，不满足时不得生成或上传正式产物。
- **应该**：原则上必须执行，只有明确记录原因后才可以例外。
- **可以**：按具体场景选择。

## 2. 事故背景

PiLauncher `0.1.53` 曾出现同一版本号对应不同二进制的情况，其中一份产物修改了已经执行过的初始迁移 `20260101000001_initial_schema.sql`。SQLx 检测到数据库中保存的校验值与新程序内嵌迁移不一致，拒绝初始化数据库，应用随后以退出码 `101` 结束，用户看到的现象是窗口白框闪现后消失。

该事故说明：

1. 已发布迁移即使只修改注释、空格或换行，也会改变 SQLx 校验值。
2. 同一个版本号重复构建和覆盖发布，会导致客户端无法区分不同代码产物。
3. 只测试全新数据库不能覆盖真实用户的升级风险。
4. 启动关键依赖失败时必须提供可见错误和可定位日志，不能静默退出。

## 3. 不可违反的核心规则

1. **已进入任何用户构建的迁移文件永久不可修改、删除、重命名或重新排序。**
2. 数据库结构发生变化时，**必须新增一个版本号更大的迁移文件**。
3. **一个应用版本只能对应一组确定的源码、二进制、安装包和签名。**
4. 已上传或已向用户提供的版本，**禁止使用相同版本号重新构建并覆盖产物**。
5. 正式产物**必须由 CI 从干净、可追溯的 Git 提交生成**；本地构建只能用于测试。
6. 数据库初始化或迁移失败时，**禁止自动删除数据库、清空数据目录或创建空数据库替换原库**。
7. 发布前**必须使用历史数据库执行升级测试**，不能只验证全新安装。
8. 缺少签名私钥、测试失败或产物校验不一致时，**禁止上传更新服务器**。

## 4. 数据库迁移规范

### 4.1 文件命名

迁移文件采用以下格式：

```text
YYYYMMDDHHMMSS_description.sql
```

示例：

```text
20260101000001_initial_schema.sql
20260823000001_add_download_tasks.sql
20260823000002_add_download_task_status_index.sql
```

要求：

- 时间版本必须全局唯一并严格递增。
- 描述使用小写 snake_case。
- 一个迁移只处理一个清晰、可审查的结构变更主题。
- 禁止复用已经出现过的版本号。

### 4.2 已发布迁移不可变

以下操作全部禁止：

- 修改旧迁移的 SQL。
- 修改旧迁移的注释、空格、编码或换行符。
- 为了“整理结构”合并多个旧迁移。
- 删除看似已经无用的旧迁移。
- 修改旧迁移后直接更新 `_sqlx_migrations.checksum` 绕过校验。

当前初始迁移由 `src-tauri/build.rs` 锁定 SHA-384。其内容发生任何变化时，构建必须直接失败，并提示恢复旧文件、创建新迁移。

所有迁移 SQL 还必须由仓库根目录 `.gitattributes` 强制使用 LF：

```gitattributes
/src-tauri/migrations/*.sql text eol=lf
```

禁止删除或放宽该规则。SQLx 按原始文件字节计算校验值；同一 SQL 的 LF 和 CRLF 会产生不同校验值，并导致不同平台构建出的程序互不兼容。构建门禁应校验磁盘上的真实字节，不得先将换行标准化后再计算哈希，否则只能掩盖错误产物。

### 4.3 正确的结构修改方式

禁止直接修改初始迁移：

```sql
-- 错误：直接编辑已经发布的 CREATE TABLE
CREATE TABLE instances (..., new_column TEXT);
```

必须新增迁移：

```sql
-- 20260823000001_add_new_column_to_instances.sql
ALTER TABLE instances ADD COLUMN new_column TEXT;
```

新增表或索引时，应使用明确且可重复诊断的 SQL：

```sql
CREATE TABLE download_tasks (
    id TEXT PRIMARY KEY,
    status TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);

CREATE INDEX idx_download_tasks_status
ON download_tasks(status);
```

不要用 `IF NOT EXISTS` 掩盖设计错误或同名对象结构不一致。只有在明确需要兼容重复执行且结构已经经过验证时才可以使用。

### 4.4 数据迁移要求

涉及已有数据转换时必须：

1. 明确旧值、空值、异常值和重复值的处理策略。
2. 在添加 `NOT NULL`、唯一索引或外键前完成数据清理。
3. 保证迁移在真实数据量下不会长时间锁死启动流程。
4. 对不可逆转换说明回滚方式和备份位置。
5. 为关键记录补充迁移前后数量或一致性验证。

禁止：

- 使用 `DROP TABLE`、`DELETE FROM` 或无条件覆盖完成“修复”，但没有备份和验证。
- 在无法识别旧结构时猜测并修改用户数据库。
- 捕获迁移错误后继续以不完整数据库启动应用。

### 4.5 迁移校验异常处理

发现 `migration ... was previously applied but has been modified` 时：

1. 立即停止发布或回滚更新服务中的问题版本。
2. 保存用户数据库和启动日志，不执行删除或重建。
3. 比对数据库 `_sqlx_migrations` 中的版本、描述和校验值。
4. 比对正式产物内嵌迁移与仓库迁移。
5. 确认历史结构完全等价后，才可以为明确、已知的历史校验值编写兼容逻辑。
6. 未知校验值必须失败关闭并提示用户，不得自动接受。

兼容逻辑必须采用明确允许列表，禁止“把任意旧校验值更新成当前值”。

## 5. 应用版本规范

### 5.1 版本一致性

每次发布必须同步更新：

- `src-tauri/Cargo.toml` 中的 `package.version`。
- `src-tauri/tauri.conf.json` 中的 `version`。
- `src-tauri/Cargo.lock` 中 PiLauncher 自身版本。

三个位置的版本必须完全一致。

### 5.2 版本唯一性

一旦某版本满足以下任一条件，即视为已发布：

- 已上传更新服务器。
- 已创建 Git Tag 或 GitHub Release。
- 已发送给外部测试用户。
- 已经可以通过自动更新接口获取。

已发布版本禁止覆盖。发现问题时必须发布更高版本：

```text
正确：0.1.54 有问题 → 修复并发布 0.1.55
错误：修改代码后重新上传另一份 0.1.54
```

### 5.3 版本与构建身份

启动日志必须至少记录：

- 应用版本。
- 初始迁移指纹。
- 启动时间和关键启动阶段。

正式流程还应该记录：

- Git commit SHA。
- 安装包 SHA-256。
- 构建平台和架构。
- CI 运行编号。
- 签名状态。

这些信息用于证明某个用户实际运行的是哪一份产物。

## 6. 正式发布流程

### 6.1 发布前准备

1. 确认工作区干净，所有发布内容已提交。
2. 确认目标版本未存在于 Git Tag、Release、更新服务器或制品仓库。
3. 同步修改 Cargo、Tauri 和锁文件版本。
4. 审查 `src-tauri/migrations/`：旧文件不得变化，新迁移版本必须唯一。
5. 完成 Rust、TypeScript、前端生产构建和数据库升级测试。
6. 创建发布提交和唯一 Git Tag。

### 6.2 CI 构建

正式构建必须由 CI 执行以下步骤：

```text
检出唯一提交
  → 验证版本一致且未发布
  → 验证旧迁移完整性
  → 安装锁定依赖
  → 执行测试
  → 执行生产构建
  → 生成安装包
  → 使用正式私钥签名
  → 计算并保存 SHA-256
  → 执行安装与升级冒烟测试
  → 上传不可变制品
```

CI 必须在以下情况失败：

- Git 工作区在构建过程中产生非预期差异。
- 三处应用版本不一致。
- 版本或 Tag 已经存在。
- 已发布迁移校验发生变化。
- 迁移 SQL 未按 `.gitattributes` 以 LF 检出。
- Rust、TypeScript、测试或生产构建失败。
- 缺少正式签名私钥。
- 安装包版本与配置版本不一致。
- 升级测试退出码异常、数据库检查失败或没有完成前端首帧。

### 6.3 上传与发布

发布人员必须：

1. 使用 CI 生成的签名产物，不使用本地 `target/` 中的文件。
2. 核对安装包文件名、内部版本和 SHA-256。
3. 核对更新接口返回的新版本、目标平台、架构、URL、签名和哈希。
4. 先灰度发布，再逐步扩大范围。
5. 保留上一稳定版本的安装包、签名和更新元数据，供紧急回滚使用。

## 7. 升级测试矩阵

每个正式版本至少验证以下数据库场景：

| 场景 | 数据来源 | 必须验证 |
| --- | --- | --- |
| 全新安装 | 无数据库、无配置 | setup 正常显示，数据库创建成功，首帧完成 |
| 上一稳定版升级 | 上一个正式版本生成 | 所有迁移成功，用户数据保留，功能可用 |
| 较老版本升级 | 至少一个长期未更新版本 | 连续迁移成功，无校验冲突 |
| 真实数据副本 | 脱敏后的用户数据库 | 数据完整、启动耗时可接受、无结构遗漏 |
| 异常退出恢复 | 迁移或安装中断状态 | 不清库、不重置目录，错误可见且可诊断 |

每个场景必须检查：

```sql
PRAGMA quick_check;
SELECT version, description, success, hex(checksum)
FROM _sqlx_migrations
ORDER BY version;
```

还必须确认：

- 进程至少持续运行 15 秒。
- 退出码不是 `101`。
- 日志包含 `native.database.initialize.complete`。
- 日志包含 `frontend.react_first_commit`。
- 日志包含 `frontend.first_animation_frame`。
- 日志不包含迁移校验冲突、panic 或数据库重建行为。
- 关键用户数据在升级前后数量和内容一致。

## 8. 启动失败与用户数据保护

数据库初始化失败时应用必须：

1. 记录具体错误、应用版本、迁移指纹和数据库路径。
2. 显示用户可见的启动失败提示。
3. 告知用户数据没有被删除，并提供启动日志位置。
4. 保留数据库、WAL、SHM 和配置文件用于恢复。
5. 退出前不得写入默认数据目录覆盖用户选择。

应用禁止：

- 因数据库错误自动删除 `pilauncher_data.db`。
- 把数据库改名后静默创建空库继续启动。
- 清空用户核心数据目录。
- 自动更新未知迁移校验值。
- 只显示白框后无提示退出。

## 9. 紧急事故处理流程

发生升级后集中闪退或白框退出时：

1. 暂停更新接口，阻止更多客户端获取问题版本。
2. 记录问题版本、安装包 SHA-256、发布时间和影响平台。
3. 获取启动日志、退出码、安装路径和数据库迁移记录。
4. 使用问题安装包和历史数据库稳定复现。
5. 禁止让用户卸载、清库或手工修改数据库作为首选方案。
6. 从最后稳定提交创建更高版本的修复分支。
7. 修复后执行完整升级矩阵，并发布新的版本号。
8. 恢复更新服务并监控启动成功率和错误日志。
9. 完成事故复盘，补充自动化门禁。

如果必须修复数据库，必须先创建可验证备份，并记录每一项变更。任何自动修复都只能处理已经确认结构等价的已知历史状态。

## 10. 发布检查清单

### 10.1 开发人员

- [ ] 没有修改、删除或重命名任何已发布迁移。
- [ ] 数据库变化通过新的唯一迁移实现。
- [ ] 迁移覆盖空值、异常值、重复值和失败路径。
- [ ] 不存在删除用户数据库或自动清空目录的逻辑。
- [ ] Rust 测试和相关前端检查通过。

### 10.2 发布人员

- [ ] Cargo、Tauri、Cargo.lock 版本一致。
- [ ] 目标版本、Tag 和更新产物从未发布过。
- [ ] 构建来自干净、唯一的 Git 提交。
- [ ] 安装包由 CI 生成并使用正式私钥签名。
- [ ] 已记录安装包 SHA-256 和 CI 运行编号。
- [ ] 全新安装、上一版本升级、旧版本升级全部通过。
- [ ] 真实安装目录启动至少存活 15 秒并完成首帧。
- [ ] `PRAGMA quick_check` 返回 `ok`。
- [ ] 更新接口中的版本、URL、平台、架构和签名正确。
- [ ] 上一稳定版本仍可用于回滚。

### 10.3 发布后监控

- [ ] 检查数据库初始化失败数量。
- [ ] 检查退出码 `101`、panic 和白框退出反馈。
- [ ] 检查前端首帧与启动超时指标。
- [ ] 检查更新下载和签名验证失败率。
- [ ] 灰度稳定后再扩大更新范围。

## 11. 当前项目防线

截至 `0.1.54`，项目已具备以下保护：

- `src-tauri/build.rs` 在构建期验证初始迁移 SHA-384。
- 启动日志记录应用版本和初始迁移指纹。
- 数据库初始化失败时显示错误和日志位置。
- 初始迁移只允许明确识别的历史校验值进入兼容修复路径。
- 生产启动链路记录数据库完成、前端提交和首帧阶段。

后续应继续补充：

- CI 版本一致性和版本唯一性检查。
- 自动化历史数据库升级矩阵。
- 安装包签名与哈希验证。
- 正式安装后的进程存活和首帧冒烟测试。
- 脱敏诊断包及发布后启动成功率监控。

## 12. 结论

数据库迁移是发布历史的一部分，不是可以反复编辑的普通源码。PiLauncher 的正式发布必须同时保证：

> 旧迁移永远不改。  
> 已发布版本永远不覆盖。  
> 正式产物只由 CI 从干净提交生成。  
> 升级失败绝不以删除用户数据作为恢复手段。
